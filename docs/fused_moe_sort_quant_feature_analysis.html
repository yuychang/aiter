Executive summary

What changed Route sorting, BF16→MXFP4 activation quantization, and routed-output zeroing now share one 16-CTA HIP launch.
Second optimization FlyDSL stage-1 GEMM can gather E8M0 scales from compact token-major storage, removing the scale-expansion launch.
Scope Opt-in, gfx950-only, H=7168, block_m=32, M=1…128, and three expert/top-k routes.
Core result. The optimized path reduces preprocessing from separate sort, quantize, and scale-layout conversion launches to one fused launch. The implementation retains the old path as a guarded fallback.
Important qualification. The “~4 µs scale expansion” and “5–12% stage-1 compact-scale cost on multi-K-wave rows” figures come from the feature commit rationale. They are not reproduced by this report and should be tracked with benchmark artifacts before enabling the feature by default.

Assessment

The design is technically coherent: it fuses launch-bound work, reuses sorted IDs already loaded into LDS to address compact scales, adds cache identity for the new compile-time variant, and gates every important kernel assumption. Operator-level and GEMM-consumer correctness coverage is strong. The main remaining weakness is integration confidence: no pytest currently drives the complete public fused_moe(...) dispatch with the environment gates enabled.

Problem and approach

MXFP4 MoE decode works on very small token batches. At that scale, a few microseconds of launch overhead can be a material fraction of layer latency. Before this feature, stage-1 preparation was split across independent GPU operations:

  1. Sort token/top-k routes by expert and pad each expert to 32 rows.
  2. Quantize BF16 activations into packed MXFP4 and produce one E8M0 scale per 32 values.
  3. Expand token-major scales into sorted-row order for stage-1 GEMM.

The key architectural decision is to leave quantized activations and scales in original-token order. Route sorting produces metadata only. Stage-1 GEMM already gathers activations using packed sorted IDs, so the compact-scale extension derives the same token index and gathers that token’s scale row. This avoids materializing a duplicate scale tensor in sorted-row order.

Packed sorted ID contract

A valid sorted entry stores (topk_slot << 24) | token_id. Padded rows use token_id == M as a sentinel. The compact-scale consumer masks the lower 24 bits, checks the token against M, and only then forms token * scale_dwords_per_token + k_offset. The producer and consumer therefore share an implicit binary contract that deserves explicit centralization (see improvement 4).

Fused HIP kernel

The new public operation is declared in aiter/ops/moe_sorting_opus.py and implemented in csrc/py_itfs_cu/moe_sorting_opus_kernels.cu. It launches 16 CTAs with 1024 threads each. CTA 0 builds route metadata; CTAs 1–15 quantize activations. All CTAs first cooperate in zeroing the routed output buffer.

Sorting work in CTA 0

  1. Build an LDS expert histogram with atomics.
  2. Round expert counts to 32-row blocks and perform a DPP prefix scan.
  3. Scatter packed token/top-k IDs and route weights into expert regions.
  4. Fill padding rows with the token-count sentinel.
  5. Write total padded rows and original token count into num_valid_ids.
  6. Emit one expert ID per 32-row sorted block.

Quantization work in CTAs 1–15

The model dimension is divided into 224 groups of 32 BF16 values. For each group, a wave computes absolute maximum, encodes an E8M0 scale, and invokes gfx950’s packed scaled FP4 conversion builtin. The output is 16 packed bytes and one scale byte per group. The kernel is intentionally specialized:

The direct C++ wrapper uses fatal AITER_CHECK validation and the non-gfx950 device path can trap. The Python dispatch gate prevents this in normal fused_moe use, but direct callers of the public operation still face process-level failure for unsupported inputs.

Dispatch and safety gates

Dispatch is opt-in through SGLANG_AITER_FUSED_DECODE_SORT_QUANT. Compact scales use SGLANG_AITER_FUSED_DECODE_COMPACT_SCALE, or inherit the first variable when unset. Accepted enabled values are auto, 1, true, on, and yes; unset or any other value disables the optimization.

The guard correctly uses live runtime architecture detection rather than a build-target environment setting. Detection failures return to the legacy path. If compact-scale eligibility fails after fused sort/quant succeeds, the wrapper runs the conventional scale-layout conversion; this preserves correctness while retaining part of the launch reduction.

API threading

fused_moe_2stages now accepts prequantized_a1, prequantized_a1_scale, and prequantized_a1_scale_compact. Supplying prequantized activation skips the old stage-1 quantization block. Explicit ValueError checks ensure the scale is present and the quantization type is compatible.

Compact-scale FlyDSL GEMM consumer

mixed_moe_gemm_2stage.py adds the compile-time a_scale_compact option. It is valid only for FP4 activations, tile_m=32, tile_k=256, sort_block_m=32, and no split-K. Compact variants receive the _asc4 module suffix to prevent JIT disk-cache aliasing.

Why the load must be deferred

Conventional scales are already in sorted-row order and can be prefetched independently. Compact scales need the original token ID, which stage 1 obtains from sorted IDs copied into LDS. The implementation splits A-scale and B-scale prefetch and waits until the sorted-ID LDS write is visible before gathering A scales. This ordering is essential; moving the compact load back into the conventional prefetch phase would create a data dependency violation rather than merely a performance regression.

Trade-off

Compact storage saves a conversion launch and avoids the larger sorted-row scale tensor, but makes the GEMM’s A-scale access indirect. The commit notes a 5–12% isolated stage-1 cost for tuner-selected multi-K-wave rows at very small M. The end-to-end decision intentionally favors the saved launch, reported at roughly 4 µs against a 30–65 µs layer. This is a sound layer-level objective, provided those measurements remain stable across driver, compiler, and model revisions.

Related tuning-objective change

Commit 1c87c39f is adjacent to the fused feature and changes the two-stage tuner in gemm_moe_tune.py. It keeps fused and non-fused stage-1 candidates distinct until launch costs are included, charges non-fused candidates for intermediate quantization consumed by stage 2, and minimizes unrounded stage-1 + stage-2 latency.

This matters conceptually: choosing the fastest GEMM1 in isolation can pick a slower layer. The compact-scale feature makes that distinction more visible because its indirect scale gather can lose locally while winning globally by deleting a launch. CPU tests cover candidate deduplication, quantization penalties, pair selection, and rounding ties.

Where the feature can be improved

Priorities below balance correctness risk, performance confidence, and maintenance cost. “P0” means the most valuable next step, not that a known correctness failure exists.

P0 Add a full public-dispatch regression test

Exercise fused_moe(...) with both environment variables enabled, real tuned metadata, and supported production routes. Compare the final layer output to the legacy path, verify the compact gate was selected, and repeat inside CUDA graph capture/replay. The current tests prove the two new pieces independently but not their complete wiring, metadata selection, activation, stage 2, and reduction.

P0 Make public-op failure recoverable

Replace user-input AITER_CHECK process aborts with exceptions surfaced through the PyTorch extension boundary, or expose a checked Python wrapper and clearly mark the raw op internal. A public symbol whose unsupported route can terminate the process is disproportionately risky for serving systems. Device-capability rejection should happen entirely on the host before launch.

P1 Track end-to-end performance continuously

Store benchmark metadata and thresholds for representative M, route, and k_wave combinations. Report fused kernel time, optional scale-sort time, GEMM1 time, and complete layer time separately. This catches the key failure mode where GEMM1 improves while layer latency regresses—or the reverse. Include ROCm, compiler, clock mode, and GPU SKU in artifacts.

P1 Generate route support from one source

The C++ macro AITER_MXFP4_SORT_QUANT_ROUTES and Python set _FUSED_DECODE_SORT_QUANT_ROUTES must remain synchronized manually. Generate one side from a shared manifest, export supported tuples from the compiled module, or add a build/test query that compares them. A stale Python superset is fatal; a stale subset silently leaves performance unused.

P1 Centralize the packed-ID ABI

Token mask 0x00ffffff, top-k shift 24, and sentinel semantics appear in producer, consumer, and tests. Define shared constants/helpers and document maximum token/top-k values. This makes future changes to routing metadata auditable and prevents subtle disagreement between HIP and FlyDSL.

P2 Profile and adapt the quantization CTA split

Fifteen fixed quantization CTAs are likely under-filled at M=1–4, while the sort remains serialized in CTA 0. Profile wave occupancy, execution overlap, and tail efficiency. Candidate experiments include M-dependent CTA counts, combining tiny-M quant work with the sorting CTA after metadata completion, or persistent work distribution. Any change must preserve graph-static launch behavior and avoid increasing synchronization overhead.

P2 Improve observability and configuration semantics

Add a debug/telemetry reason code for each fallback: unsupported architecture, route, kernel family, split-K, EP, or compact-scale tile. The current one-time warning only covers the aux-sort path. Also consider AITER-scoped environment names with compatibility aliases; SGLANG_AITER_* couples a core library optimization to one integration layer.

P2 Expand support only from measured demand

Expert parallelism, additional routes, other hidden sizes, and M>128 are unsupported. Generalization should be data-driven because each dimension can alter LDS use, histogram cost, quant work distribution, and tuning. A small code-generated specialization table is preferable to turning all dimensions into runtime values and weakening optimization.

P3 Reduce API ambiguity

mxfp4_moe_sort_quant_fwd is distinct from the existing mxfp4_moe_sort_quant aux-sort kernel. Rename or namespace the two operations around their output contracts—such as “compact token scales” versus “aux sorted output”—and add shape/dtype details to docstrings.

Operational guidance

  • The optimization is off by default. Enabling it never widens kernel support; all gates still apply.
  • Enable sort+quant first and inspect fallback reasons. Compact scales inherit that setting unless explicitly overridden.
  • Do not infer activation from the environment variable alone; confirm selected kernel metadata is FlyDSL FP4 with compatible tiles.
  • Use runtime gfx detection. A build configured for gfx950 does not prove the executing device is gfx950.
  • For unsupported EP, split-K, aux-sort, route, or shape cases, the expected behavior is legacy-path fallback.
Recommended rollout criterion. Enable by default only after public-dispatch correctness tests pass and end-to-end benchmark artifacts show a stable win over supported production shapes across the deployment ROCm/JIT matrix.
